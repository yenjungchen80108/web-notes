# 2. Data Models and Query Languages

## Polyglot Persistence

“Polyglot Persistence” 是一個在現代系統設計中非常重要的概念，尤其常見於大型應用或微服務架構中。

⸻

🧠 定義：什麼是 Polyglot Persistence？

Polyglot Persistence（多語言持久化） 指的是一個系統中根據不同需求，同時使用多種不同類型的資料庫技術，而不是只用一種資料庫來處理所有資料。

這個詞來源於 “Polyglot Programming”（多語言編程）的概念。

⸻

📦 為什麼需要 Polyglot Persistence？

不同的資料類型、存取模式、查詢方式，有不同的最佳資料庫：

| 資料需求                             | 最佳資料庫類型                   |
| ------------------------------------ | -------------------------------- |
| 關聯式資料（有 schema，JOIN 操作多） | RDBMS（如 PostgreSQL, MySQL）    |
| 文檔型資料、彈性 schema              | NoSQL（如 MongoDB）              |
| 快速查詢 key-value、快取             | Redis, DynamoDB                  |
| 圖形資料、關係圖                     | Graph DB（如 Neo4j）             |
| 實時分析、大數據                     | Elasticsearch、ClickHouse、Druid |
| 時序資料                             | InfluxDB、TimescaleDB            |

⸻

🧩 範例：E-Commerce 平台

一個真實世界的電商系統可能這樣使用：

| 功能                   | 使用的資料庫           |
| ---------------------- | ---------------------- |
| 使用者帳戶、訂單       | PostgreSQL             |
| 商品 catalog、彈性規格 | MongoDB                |
| 推薦系統、用戶圖譜     | Neo4j                  |
| 快取熱銷商品           | Redis                  |
| 日誌搜尋與分析         | Elasticsearch          |
| 活動追蹤紀錄           | ClickHouse or BigQuery |

這就是 Polyglot Persistence。

⸻

⚠️ 優點與挑戰

✅ 優點

- 根據需求選擇最適資料庫 → 效能與彈性最佳化
- 更好地支持複雜或多樣的資料模式

❌ 缺點

- 開發與維運變得更複雜（需熟悉多種資料庫）
- 資料一致性處理更具挑戰（跨 DB 的交易）
- 備份、權限、監控變得多系統化

⸻

💬 與微服務的關聯

在微服務架構中，每個服務通常可以有自己的資料庫（Database per service），這正好自然形成 Polyglot Persistence。

例如：

- UserService 用 MySQL
- ProductService 用 MongoDB
- RecommendationService 用 Neo4j

這樣設計符合責任劃分與彈性伸縮性。

⸻

📌 總結一句話：

Polyglot Persistence = 按需選擇資料庫技術，讓資料結構與查詢方式達到最佳化。

## Impedance Mismatch（阻抗不匹配）

它常常出現在「應用程式（尤其是物件導向程式）與資料庫」之間的資料表示與操作不一致問題。

⸻

📌 定義：什麼是 Impedance Mismatch？

Impedance Mismatch 是指「程式語言中的物件模型」與「資料庫中的關聯模型」之間的資料結構與行為上的不一致，造成開發與維護上的困擾。

⸻

🧱 常見的不一致項目

| 程式語言（OOP）           | 關聯式資料庫（RDBMS）          |
| ------------------------- | ------------------------------ |
| 類別 Class / 物件 Object  | 表格 Table / 欄位 Field        |
| 屬性（property）          | 欄位（column）                 |
| 巢狀物件（nested object） | 外鍵（foreign key）/ 多表 join |
| 繼承 Inheritance          | 沒有直接支援                   |
| 多型 polymorphism         | 無法直接表示                   |

這導致了你在開發時常常要「手動轉換」資料結構，造成很多冗長的程式碼與潛在 bug。

⸻

🔧 舉個簡單例子

🧑‍💻 JavaScript 程式碼

```js
class User {
  constructor(name, email, address) {
    this.name = name;
    this.email = email;
    this.address = {
      street: "Main St",
      city: "Taipei",
    };
  }
}
```

🗄️ 在資料庫中：

Table: users

| id | name | email | ...

你必須：

- 把 address.street 拆成 address_street
- 把巢狀結構扁平化
- 在資料庫讀出來後再組回 object

⸻

🤯 為什麼這是個問題？

- 你需要額外的 mapping layer（Object-Relational Mapping, ORM）
- 難以處理巢狀資料或繼承（OOP → DB 很難直接對應）
- 轉換過程容易出錯
- 不同層的語意不一致：object 是狀態與行為，table 只有資料

⸻

🛠 解法與應對方式

1. 使用 ORM（Object Relational Mapper）

例如：

- TypeORM / Prisma（Node.js）
- Hibernate（Java）
- Entity Framework（.NET）

這些工具幫你自動對應 class ↔ table，減少轉換成本

2. 避免複雜繼承結構、改用平坦資料設計

盡量讓你的物件結構接近資料表結構，減少 mismatch

3. 或者用 NoSQL（e.g. MongoDB）來原生支援物件結構

當你的資料就是巢狀、物件導向為主，NoSQL 可以減少 impedance mismatch

⸻

💬 常見出現在哪些情境？

- OOP 語言 + RDBMS（最常見的 mismatch）
- 使用 ORM 時「需要定義關聯與轉換規則」
- 微服務之間傳資料：DTO 與資料庫 schema 不一致
- API response 與資料表欄位不完全一致時

⸻

✅ 總結一句話：

Impedance Mismatch 是指程式中用物件表示資料，而資料庫用關聯式表格儲存資料時，這兩者在結構與操作上的不一致。

## Relational modal vs Network model

**the network model:**
standardized by CODASYL, it was a generalization of the hierarchical model. A record could have multiple parents/ The links between records in the network model were not foreign keys, but more like pointers in a programming languages. The way of accessing a record was to follow a path from a root record along these chains of links. This was called an access path.

However, if you didn't have a path to the data you wanted, you had to go through a lot of query code and rewrite it to handle the new access path.

**the relational model:**
the relational model is to layout all the data in the open: a relation table is a collection of ruples rows. There are no complicated links between records. The way of accessing a record was to use a foreign key to join with another table. You only need to build a query optimizer once, and then all applications that use the database can benefit from it.

> the main arguments in favor of
> the **document data model** are schema flexibility, better performance due to locality, and that for some applications it is closer to the data structures used by the application.
> the **relational model** counters by providing better support for joins, and 多對一或多對多關係.

## XML

XML 的定義

- XML (eXtensible Markup Language) 是一種用標籤 (tag) 來描述資料結構的純文字格式。
- 它的設計目標是 儲存和傳輸資料，而不是用來顯示（不像 HTML 主要用於展示）。
- XML 本質上就是一種樹狀結構的數據表示法，每個元素都由開始標籤和結束標籤包圍，可以有屬性和層級。

例子：

```xml
<user>
  <name>Emily</name>
  <age>30</age>
</user>
```

⸻

XML 和 JSON 的關係

1. 都是用來描述和傳輸資料的格式。

- XML 常見於早期的 API（SOAP、RSS 等）。
- JSON 因更簡潔直觀，近年成為 REST API 和前後端資料傳輸的主流。

2. 結構上的差異

- XML 使用標籤和屬性：

```xml
<user age="30">Emily</user>
```

- JSON 使用鍵值對：

```json
{ "user": { "age": 30, "name": "Emily" } }
```

3. 優缺點：

- XML 優點：可用 schema 驗證（XSD）、支援屬性和混合內容（文字 + 標籤）、適合複雜資料。
- JSON 優點：格式輕量、可直接對應物件結構（JS 原生支援）、解析速度快。

⸻

什麼時候用 XML?

- 舊系統（銀行、保險）或標準化協定（SOAP Web Service、RSS feed、SVG）。
- 需要更嚴謹結構和驗證時（透過 XSD）。
